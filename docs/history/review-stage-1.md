## Найденные проблемы

Воспроизведение: файл `probe/app/web/views.py` ниже, плоская раскладка (`app/` в корне).

```python
from typing import TYPE_CHECKING
from app.core.base import Repo, SqlRepo, Mongo, helper
if TYPE_CHECKING:
    from app.core import base as typing_only

def shadow(helper):
    helper()                 # параметр перекрывает helper модуля

def poly(r: Repo):
    r.save()                 # в рантайме может быть SqlRepo.save

def reassign(flag):
    x = SqlRepo()
    if flag:
        x = Mongo()
    x.save()                 # SqlRepo.save ИЛИ Mongo.save

def outer():
    def inner():
        helper()             # вызов во вложенной функции
    inner()

class Svc:
    def __init__(self, cfg):
        self.repo = SqlRepo()
    def swap(self):
        self.repo = Mongo()
    def go(self):
        self.repo.save()     # SqlRepo.save ИЛИ Mongo.save
```

`app/core/base.py`: `Repo` (методы `save`, `run`, где `run` вызывает `self.save()`), `SqlRepo(Repo)` переопределяет `save`, `Mongo` с `save`, функция `helper`.

### P0 — ложные `resolved` (нарушение главного принципа)

| # | Случай | Что выдаёт сканер | Как должно быть |
|---|---|---|---|
| 1 | `shadow`: параметр `helper()` | `resolved → base:helper` | `unresolved`: локальное имя перекрывает модульное |
| 2 | `reassign`: `x` присваивается дважды | `resolved → Mongo.save` (побеждает последнее присваивание) | `unresolved` или `inferred` со списком кандидатов |
| 3 | `Svc.go`: `self.repo` присваивается в двух методах | `resolved → Mongo.save` | то же |
| 4 | `poly(r: Repo)`: `r.save()` | `resolved → Repo.save` | `inferred`: аннотация задаёт только верхнюю границу типа, а `SqlRepo` переопределяет `save` |
| 5 | `Repo.run`: `self.save()` | `resolved → Repo.save` | `inferred`, если в репо есть подкласс, переопределяющий метод; иначе можно оставить `resolved` |
| 6 | **src-раскладка** (`src/app/...`): `from app.core.base import ...` | `imports resolved → ext:app`, то есть «app — внешний пакет» | Внутренний импорт. Нужны корни импорта (автодетект `src/` и параметр `--root`). Модуль, которого нет ни в репо, ни в stdlib (`sys.stdlib_module_names`), ни в установленных пакетах, → `unresolved`, а не «resolved external» |
| 7 | Импорт под `if TYPE_CHECKING:` | обычное `imports resolved` и участие в reflexion | Пометка `type_only: true`; по умолчанию не поднимать в reflexion (это не зависимость времени выполнения) |

Пункт 6 критичен: на популярной src-раскладке **все внутренние зависимости становятся внешними**, и reflexion не видит ни одной связи. При этом ошибки нет, просто пустой отчёт «всё чисто».

### P1 — надёжность и полнота

8. **Одна синтаксическая ошибка роняет весь скан** (traceback). Файлы с `SyntaxError` или `UnicodeDecodeError` нужно записывать в `errors[]` карты и продолжать.
9. **Вызовы во вложенных функциях теряются целиком** (`_ScopeVisitor` не заходит внутрь). Это даёт ложные Absence в reflexion. Минимум: приписывать такие вызовы объемлющему символу.
10. Определения внутри `if`/`try` на уровне модуля не становятся узлами.
11. `from x import a, b, c, d` даёт 4 одинаковых ребра `imports`. Нужна дедупликация по `(from, to, line)` или одно ребро со списком имён.
12. Если `from pkg import name` реэкспортирован через `__init__`, вызов `name()` даёт ребро `calls` на **узел модуля**. Нужно либо проследить реэкспорт, либо оставить `unresolved`.

### P2 — объём и документация

13. **Сделано много того, что было явно запрещено ТЗ:** React/D3-приложение (~12 тыс. строк TS), сервер с вызовами Gemini API (`server.ts`, `/api/pmap/gemini-agent`), KPI-дашборд, экспорт в PDF, перф-бенчмарк, аналитика (PageRank, Tarjan, blast radius), MCP-сервер. Это размывает проверку ядра и добавляет LLM в контур, который должен быть детерминированным.

15. `CLAUDE.md`/`AGENTS.md` предписывают агентам **всегда** использовать pmap. Это преждевременно: польза карты ещё не измерена. Пока бенчмарка нет, формулировка должна быть «можно использовать».
16. `.gitignore` не исключает `__pycache__/` и `.pmap/`. В репозитории лежат `.pyc` двух версий Python.

## Задание на этап 1.1 (для исполнителя)

Цель: сканер не должен утверждать ничего, что не доказано статически. Новых функций не добавлять.

1. Исправить P0 (пункты 1–7). Правило для `resolved`: цель вызова определяется **единственным** образом с учётом локальной области видимости и всех присваиваний в ней. Иначе `inferred` (с полем `candidates: [...]`, если кандидатов несколько) или `unresolved`.
   - Локальные имена (параметры, присваивания, `for`, `with`, `except as`, импорты внутри функции) перекрывают модульные.
   - Аннотация параметра или атрибута даёт не больше чем `inferred`.
   - Тип из конструктора даёт `resolved`, только если в области видимости ровно одно присваивание этой переменной или атрибута.
   - `self.method()` даёт `inferred`, если какой-либо подкласс в репо переопределяет метод.
2. Корни импорта: автодетект `src/`, флаг `--root` (можно несколько), учёт `pyproject.toml` при наличии. Внешние модули определять через `sys.stdlib_module_names` и `importlib.util.find_spec`; неизвестное помечать `unresolved`.
3. `TYPE_CHECKING`: поле `type_only` в ребре; reflexion по умолчанию их не учитывает, флаг `--include-type-only` включает.
4. Исправить P1 (пункты 8–12).
5. **Регрессионные тесты на каждый пункт 1–12**, используя пример выше и src-вариант. Тест должен проверять конкретный `confidence` конкретного ребра.
