![Method Project Map: пакеты по слоям и связи выбранного пакета](docs/images/overview-ru.png)

**Method Project Map** читает проект статически (Python, TypeScript / JavaScript, Go, Java, Kotlin, C#, Swift, Dart / Flutter, Rust, C / C++) и рисует его устройство: пакеты, файлы, классы, функции и кто кого импортирует, вызывает и от кого наследуется. ИИ и интернет здесь не участвуют: карта вычисляется, поэтому она всегда одинакова и сама обновляется, когда меняется код.

У одной карты три задачи:

- **Для человека** — интерактивная блок-схема в браузере. Пакеты разложены по слоям, от точек входа до фундамента; клик по карточке показывает, что она использует и кто использует её. В том числе между языками: от экрана Flutter через канал платформы в Swift, Kotlin или C++ и дальше в ядро на Rust.
- **Для ИИ-агентов** (Claude Code, Codex, любой MCP-клиент) — короткая заметка сразу после правки кода. В ней названо всё, что зависит от изменённого кода в других местах: вызовы из других файлов и другая сторона каждого моста между языками. Так правка не останавливается на полпути. Плюс краткий обзор в начале сессии и точечные запросы вместо чтения целых файлов.
- **Для архитектора и CI** — задуманная архитектура (`design.yaml`), сверенная с настоящим кодом, и **пропуски между языками**: метод канала, который какая-то платформа не обрабатывает. Каждая находка — с файлом и строкой.

У каждой связи есть уровень уверенности: **подтверждена**, **возможна** или **не определена**. Карта никогда не выдаёт догадку за факт.

## Быстрый старт

Для работы инструмента нужен Python 3.9 или новее — на каком бы языке ни был ваш проект. Установщик заодно скачивает грамматики tree-sitter для остальных языков (около 15 МБ из PyPI, в `~/.pmap/venv`); чтобы пропустить их, добавьте `--python-only`.

```bash
git clone https://github.com/lstcrsdd/method-project-map.git
cd method-project-map
./install.sh          # Windows: install.bat
```

Потом откройте **Method Project Map** из «Программ» (macOS), меню «Пуск» (Windows) или меню приложений (Linux), либо выполните `~/.pmap/bin/pmap ui`. В первый раз карта спросит, какую папку проекта показать, и предложит минутное обучение.

<details>
<summary>Параметры установщика и запуск без установки</summary>

| | macOS / Linux | Windows |
|---|---|---|
| Установить и подключить Claude Code (по умолчанию) | `./install.sh` | `install.bat` |
| …подключить Codex / обоих агентов | `./install.sh --codex` / `--all` | `install.bat --codex` / `--all` |
| Установить без подключения агентов | `./install.sh --none` | `install.bat --none` |
| Не ставить грамматики других языков | `./install.sh --python-only` | `install.bat --python-only` |

Всё ставится в `~/.pmap`, плюс ярлык приложения. Отменить: `pmap disconnect --all`, `pmap shortcut --remove`, затем удалить `~/.pmap`.
</details>

## Что можно делать

| | |
|---|---|
| **Смотреть на трёх уровнях**: обзор → пакет → файл. Внутри файла видны три колонки: кто его использует, что в нём, что использует он. Клик по функции оставляет только её вызывающих и вызываемых. | ![Вид файла](docs/images/file-ru.png) |
| **Проверять архитектуру**: опишите подсистемы и разрешённые зависимости в `design.yaml`. Вид «Архитектура» и `pmap check` покажут, где код нарушает правила; `pmap check --strict` уронит проверку в CI. | ![Вид «Архитектура»](docs/images/design-ru.png) |

А ещё:

- переключаться между проектами через Finder, Проводник или список недавних;
- искать классы, функции и файлы по имени;
- смотреть код одной функции;
- открывать файл в Finder или Проводнике;
- выгружать схемы в Mermaid;
- сохранять всю карту одной самодостаточной HTML-страницей для сайта или вики;
- пользоваться интерфейсом **на русском и английском**, со встроенным справочником и пошаговым обучением.

## Языки

| Язык | Что понимает карта |
|---|---|
| **Python** | импорты (относительные, раскладка `src/`, реэкспорты), вызовы через области видимости и аннотации типов, наследование — встроено, без зависимостей |
| **TypeScript / JavaScript** | ES-модули и CommonJS, алиасы путей из `tsconfig`, реэкспорты через `index`, пакеты монорепозитория, JSX-компоненты |
| **Go** | модули `go.mod`, пакеты из нескольких файлов, методы с получателем, встраивание, интерфейсы |
| **Java / Kotlin** | пакеты, обычные, групповые и статические импорты, классы своего пакета, функции верхнего уровня Kotlin, оба языка в одном проекте |
| **C#** | пространства имён (блочные и на весь файл), `using`, `using static`, `global using`, алиасы, records, инструкции верхнего уровня |
| **Swift** | модули SwiftPM и Xcode (файлы модуля видят друг друга), `import`, протоколы, расширения, `init` |
| **Dart / Flutter** | импорты `package:` и относительные, реэкспорты через `export`, префиксы `as`, файлы `part`, виджеты, миксины, расширения |
| **Rust** | крейты и воркспейсы, файлы `mod`, `use` с `crate::` / `self::` / `super::`, реэкспорты `pub use`, блоки `impl` и трейты |
| **C / C++** | `#include`, пространства имён и `using namespace`, классы, методы, определённые вне класса (`Type::m` в .cpp), вызовы Win32 и C++/WinRT остаются за заголовками |

В одном проекте языки можно смешивать. Карта следит за типами переменных:
- через объявления и конструкторы;
- через объявленные результаты функций проекта, в том числе по цепочкам `a.b().c()`, через `?` и `unwrap()`;
- через типы полей.

В типизированных языках объявленный тип проверяет компилятор, поэтому вызов у класса проекта — **подтверждённая** связь, если ни один подкласс не переопределяет метод. Вызов через интерфейс, протокол или трейт — **возможная** связь. Значения, созданные библиотеками, карта распознаёт: вызовы у них — обращения к библиотеке, а не пробелы в карте.

Замеры на настоящем коде (вызовы, которые карта оценивает; обращения к библиотекам не считаются):

| Код | Файлов | Время | Подтверждено | Возможно | Не определено |
|---|---|---|---|---|---|
| Фреймворк Flutter (Dart) | 1 712 | 20 с | 90% | 3% | 7% |
| Go `net/http` | 157 | 0,6 с | 73% | 4% | 23% |
| Крейт Rust `time` | 164 | 0,3 с | 65% | 4% | 31% |
| Крейт Rust `openmls`, код библиотеки | 263 | 0,5 с | 61% | 0% | 39% |

Неопределённым остаётся то, чего статический анализ действительно не видит:
- код, сгенерированный макросами;
- замыкания без типов;
- значения функций без объявленного типа.

`pmap langs` показывает, какие грамматики установлены, `pmap langs install` добавляет их.

## Мосты между языками

Некоторые вызовы не проверяет ни один компилятор. Приложение на Flutter обращается к Swift, Kotlin и C++ по имени канала и имени метода — обычным строкам. Dart, Swift, C++ и Kotlin обращаются к ядру на Rust по именам символов. Переименуйте одну сторону — приложение соберётся, а упадёт уже во время работы. Карта связывает обе стороны:

| Мост | Откуда | Куда |
|---|---|---|
| Каналы Flutter (методы, события, сообщения) | `invokeMethod('pause')` в Dart и обратно | ветка `case "pause":` / `"pause" ->` / `method_name() == "pause"` в Swift, Kotlin, Java, C++ |
| C ABI (FFI) | `lookup` / `@Native` из `dart:ffi`, Swift, C/C++, Go (cgo) | функции Rust с `#[no_mangle]`, определения на C, `@_cdecl`, `//export` |
| JNI | `external fun` / `native` в Kotlin и Java | `Java_<пакет>_<класс>_<метод>` на Rust или C |
| Сгенерированные привязки | Pigeon, flutter_rust_bridge, UniFFI, `invoke` в Tauri | реализация API Pigeon на Swift / Kotlin / Java, функция или команда на Rust |
| Передачи через систему (возможные связи) | NetworkExtension (Apple): приложение запускает своё расширение; `startService(Intent(…))` в Android | провайдер расширения; `onStartCommand` сервиса |

На [examples/audio_player](examples/audio_player) — плагине Flutter, у которого на Windows нет ветки для `setSpeed`:

```text
$ cd examples/audio_player
$ pmap check .
No design map (design.yaml or PROJECT.mdm): only the links between languages are checked.

Links between languages: 25 (channel 25)
[!] GAPS (a platform that handles the channel does not handle this method):
  ✗ channel audio/player: "setSpeed" is called from Dart (lib/player.dart:59) but C/C++ (windows) does not handle it (windows/audio_player_plugin.cpp:43)
```

**Пропуск** — метод канала, который одна из платформ не обрабатывает. Вызов падает только на этой платформе. `pmap check .` перечисляет пропуски с `design.yaml` и без него, а `--strict` останавливает на них сборку в CI.

## Для ИИ-агентов

```bash
pmap connect --claude      # или --codex, --gemini, --all; отменить: pmap disconnect --all
```

Для Claude Code и Codex команда ставит:

- **заметку после каждой правки** (хук `PostToolUse`). В ней сказано, что зависит от только что изменённого кода в других файлах и на других языках. Если ничего не зависит, заметки нет, и в одной сессии она не повторяется. После правки `AudioPlayer.pause` в плагине из примера:

  ```text
  Method Project Map — code elsewhere depends on what you just changed; keep it in step:
  AudioPlayer.pause (lib/player.dart:41)
    → android/src/main/kotlin/dev/example/audio_player/AudioPlayerPlugin.kt:112  AudioPlayerPlugin.onMethodCall  (Kotlin, channel audio/player "pause")
    → ios/Classes/AudioPlayerPlugin.swift:88  AudioPlayerPlugin.handle  (Swift, channel audio/player "pause")
    → windows/audio_player_plugin.cpp:57  AudioPlayerPlugin::HandleMethodCall  (C/C++, channel audio/player "pause")
    used in 1 other file:
      lib/ui/controls.dart:23  Controls.onPause
  ```

- короткий **обзор в начале сессии** (хук `SessionStart`): языки, мосты между ними и пропуски, затем пакеты и файлы;
- навык, правило и MCP-сервер с инструментами `pmap_overview`, `pmap_find`, `pmap_show`, `pmap_source`, `pmap_check`, `pmap_stale` и `pmap_scan`.

Каждое изменение — помеченный блок с резервной копией. Codex запускает хуки после одобрения: откройте в Codex `/hooks`.

То же самое можно поставить плагином:

```text
/plugin marketplace add lstcrsdd/method-project-map      # Claude Code
/plugin install project-map@method-project-map
```

Агенты следуют одному протоколу, каким бы способом они ни получали карту. На связи `resolved` можно полагаться, `inferred` нужно проверить, для `unresolved` надо читать код. Подробно — в [docs/AGENT_PROTOCOL.md](docs/AGENT_PROTOCOL.md).

### Испытание

Испытание проводилось на Codex и проекте в 29 тысяч строк, со скрытыми тестами, которых агент не видит: 6 задач на исправление ошибок × 2 режима × 5 прогонов.

| | С картой / без карты |
|---|---|
| Исправления, прошедшие скрытые тесты | 60 из 60 в обоих режимах |
| Код, прочитанный агентом | **0,55×** (95% доверительный интервал 0,49–0,59) |
| Выходные токены | 0,85× |
| Входные токены в сумме | 0,93× (интервал 0,83–1,02, разница не значима) |

Агенты, которым о карте только сообщили, ею почти не пользовались: ни в испытании, ни в настоящих сессиях они не вызывали команды карты. Обзор сокращал чтение кода, но стоил примерно столько же токенов, сколько экономил, а исправления без него были не хуже. Поэтому обзор стал короче, а главным стала заметка после правки: карта подаёт голос, когда агент меняет код, от которого зависят другие файлы и языки. Следующее испытание проверит это на задачах, проходящих через несколько языков. Отчёты — в [bench/reports](bench/reports).

## Вместе с mDm

[mDm](https://method-network.com/) — редактор функциональных схем той же сети Method Network. Схема, которую он отдаёт кодовому агенту (`PROJECT.mdm`), служит этой карте проектом: агент дописывает у функций строку `код:` с путями, и `pmap check .` сверяет связи в коде со связями на схеме. Обзор для агента начинается со списка функций и того, где они в коде. Подробно — в [руководстве](docs/guide.ru.md#схема-mdm-вместо-designyaml).

## Как это работает

1. **Сканирование.** Python-файлы читает встроенный в Python парсер `ast`, остальные языки — tree-sitter. Импорты, вызовы и базовые классы разрешаются через области видимости, корни импорта (раскладка `src/` определяется сама) и аннотации типов. Связь, которую нельзя доказать, помечается как `inferred` со списком кандидатов или как `unresolved`. Молча в факт она не превращается.
2. **Карта.** Результат — *фактическая карта* в формате PMF (`.pmap/actual.json`) с хешами файлов, поэтому устаревшая карта никогда не используется.
3. **Сверка.** Необязательная *проектная карта* (`design.yaml`) сравнивается с фактической по модели Reflexion (Murphy & Notkin, 1995). Получаются совпадения, нарушения и пропуски.
4. **Доставка.** Одна и та же карта подаётся людям (веб-интерфейс), агентам (обзор, CLI, MCP) и CI (`pmap check`).

## Ограничения

- Проверки типов нет: вызовы у значений, тип которых карта не видит (переменные без типа, результаты библиотечных функций), остаются неопределёнными.
- Мосты между языками находятся по именам: имя канала или символа, собранное во время работы, карта не прослеживает. Objective-C и модули React Native пока не читаются.
- Сгенерированный и чужой код засоряет карту; исключите его через `.pmapignore`.
- Статический анализ «закрытого мира»: карта не видит вызовов из кода вне репозитория, подмены функций на лету и обращений по имени через `getattr`.
- Пока не проверены на реальных машинах:
  - установщик для Windows;
  - ярлыки и окна выбора папки на Windows и Linux;
  - установка плагина в Codex.

  Swift и C++ проверены только на тестовых проектах. Будем рады отчётам.

## Участие

Задачи и pull request'ы приветствуются. Перед отправкой изменения запустите тесты: `python3 -m unittest discover -s tests` на Python 3.9 или новее. После изменений в `pmap/` пересоберите плагин: `python3 scripts/build_plugin.py`. Заметки для ИИ-агентов — в [AGENTS.md](AGENTS.md).
