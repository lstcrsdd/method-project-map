# Спецификация Project Map Format (PMF) v0

**Project Map Format (PMF)** — открытый, машинно- и человекочитаемый формат представления иерархической карты программного проекта. PMF объединяет архитектурный замысел человека (**Design Map**) и статически доказанную структуру исходного кода (**Actual Map**) для:
1. **ИИ-агентов** (Claude Code, Codex и др.) — точечная навигация и сбор контекста без чтения всего репозитория.
2. **Инженеров и архитекторов** — визуализация архитектуры (Mermaid) и автоматический контроль архитектурных границ по методу **Reflexion Model** (Murphy & Notkin, 1995).

---

## 1. Уровни иерархии и типы узлов (Nodes)

Иерархия проекта делится на два слоя: **проектный (design)** и **фактический (actual)**.

| Уровень | Тип узла (`kind`) | Карта | Описание |
| :--- | :--- | :--- | :--- |
| 0 | `project` | Design | Корень проекта. Задаёт имя репозитория и глобальные настройки. |
| 1 | `subsystem` | Design | Архитектурный блок / подсистема / слой (например, `ui`, `services`, `db`). Определяется только человеком. |
| 2 | `module` | Actual | Файл исходного кода (для Python — `.py` файл) или внешний пакет (`external: true`). |
| 3 | `class`, `function`, `method` | Actual | Символы внутри модуля, извлечённые статическим анализатором. |

### Поля узла в Actual Map (`nodes[]`)
- `id` (`string`, обязательное): детерминированный идентификатор узла.
  - Для модулей репозитория: `mod:<dotted.module.name>` (например, `mod:app.services.order_service`).
  - Для внешних пакетов: `ext:<package_name>` (например, `ext:dataclasses`).
  - Для символов: `sym:<dotted.module.name>:<SymbolName>` или `sym:<dotted.module.name>:<ClassName>.<method_name>`.
  - Повторные определения с тем же именем в одной области (`if/else`, геттер и сеттер свойства) получают суффикс: `sym:m:impl#2`.
  - `<dotted.module.name>` вычисляется относительно корня импорта (раздел 2.2), а не корня репозитория.
- `kind` (`"module" | "class" | "function" | "method"`, обязательное).
- `name` (`string`, обязательное): короткое имя (`OrderService`, `create_order`).
- `qualified_name` (`string`, обязательное): полное квалифицированное имя (`app.services.order_service.OrderService.create_order`).
- `parent_id` (`string | null`): `id` родительского узла (`mod:...` для класса/функции, `sym:...` для метода).
- `external` (`boolean`, по умолчанию `false`): `true` для внешних библиотек вне анализируемого репозитория.
- `signature` (`string | null`, опционально): компактная сигнатура аргументов и возвращаемого типа (например, `(order_id: int, amount: float) -> dict`), полезная для текстового контекста ИИ-агента.
- `docstring_summary` (`string | null`, опционально): первая строка docstring узла.
- `location` (`object | null`): привязка к исходному коду (обязательна для всех узлов с `external: false`).

## 2. Рёбра (Edges) и модель достоверности

Каждая связь в карте направлена от `from` (кто зависит / содержит / вызывает) к `to` (от кого зависит / кого содержит / кого вызывает).

### Поля ребра (`edges[]` и `allowed_dependencies[]`)
- `from` (`string`, обязательное) — `id` исходного узла (или `subsystem` в `allowed_dependencies`).
- `to` (`string`, обязательное) — `id` целевого узла (или `unresolved:<expr>` при `confidence: "unresolved"`).
- `kind` (`string`, обязательное) — тип связи:
  - В Design Map: `allowed_dependency` — разрешённое архитектором направление зависимости между двумя `subsystem` (`from` → `to`).
  - В Actual Map:
    - `contains` — структурная вложенность (`module` → `class`/`function`, `class` → `method`). Всегда `confidence: "resolved"`.
    - `imports` — импорт модуля или символа (`module` → `module`).
    - `inherits` — наследование класса (`class` → `class`).
    - `calls` — вызов функции, метода или конструктора класса (`function`/`method`/`module` → `function`/`method`/`class`).
- `confidence` (`"resolved" | "inferred" | "unresolved"`, обязательное в Actual Map). Главный принцип PMF: **достоверность важнее полноты**, предположение никогда не выдаётся за факт. Точные правила приведены в разделе 2.1.
- `candidates` (`string[]`, только при `confidence: "inferred"`) — все возможные цели. Если цель одна, `to` указывает на неё; если их несколько, `to` имеет вид `ambiguous:<expr>`.
- `type_only` (`boolean`, по умолчанию `false`) — импорт выполняется только под `if TYPE_CHECKING:` и не является зависимостью времени выполнения.
- `source` (`string`, обязательное в Actual Map) — каким анализатором получено ребро (например, `"python-ast-v0"`, `"scip-python"`, `"manual"`).
- `location` (`{ "path": string, "line": int } | null`) — точное место вызова или инструкции `import` в коде.

Специальные значения `to`: `unresolved:<expr>` — цель неизвестна; `unresolved:import:<module>` — импорт не найден ни в проекте, ни среди внешних модулей; `ambiguous:<expr>` — несколько кандидатов (см. `candidates`).

### 2.1. Правила уверенности (сканер `python-ast-v0`)

Анализ имён **нечувствителен к порядку выполнения**: учитываются все связывания имени во всей области видимости (параметры, присваивания, `for`, `with`, `except ... as`, импорты внутри функции, вложенные `def`/`class`, связывания во вложенных функциях). Имя, связанное двумя разными способами, никогда не даёт `resolved`.

**`resolved`** — цель единственна и доказана самим кодом:
- вызов имени, которое на уровне модуля связано ровно один раз с функцией или классом проекта (напрямую или через импорт, в том числе через реэкспорт в `__init__.py`) и не перекрыто локальным именем;
- метод экземпляра, созданного конструктором `x = Foo()`, если во всей области видимости нет других присваиваний `x`;
- `self.attr.m()`, если **все** присваивания `self.attr` в иерархии класса — конструкторы одного и того же класса;
- `self.m()`, если метод найден в классе или его предках, ни один подкласс в проекте его не переопределяет, и по пути поиска нет внешних базовых классов;
- `super().m()` при одиночном наследовании внутри проекта;
- импорт файла проекта или известного внешнего модуля (stdlib, установленный пакет, `site-packages` виртуального окружения в репозитории).

**`inferred`** — цель взята из обещания или из списка вариантов:
- тип известен только из аннотации (`def f(r: Repo)`): аннотации не проверяются во время выполнения, поэтому они не доказательство, даже без подклассов;
- у имени или атрибута несколько возможных значений (`x = A()` и `x = B()`, `try/except ImportError` с двумя источниками, условные определения);
- метод может быть переопределён подклассом (`candidates` включает переопределения);
- перед найденным методом в иерархии стоит внешний базовый класс, который может его перекрыть;
- базовый класс неоднозначен.

**`unresolved`** — ссылка есть, цель определить нельзя:
- локальное имя без известного значения (параметр без аннотации, результат вызова функции, элемент контейнера);
- аннотации `Any` / `object`;
- вызов вложенной функции, `self` внутри вложенной функции, атрибут, который не найден в иерархии;
- импорт, который не найден ни в проекте, ни среди внешних модулей; относительный импорт, не разрешившийся внутри проекта.

**Без ребра** — вызовы встроенных функций, внешних библиотек и методов значений внешних/встроенных типов (`str`, `list`, аннотации-контейнеры). Они не входят в граф проекта, и отсутствие ребра не является утверждением.

### 2.2. Корни импорта

Имя модуля вычисляется относительно **корня импорта**. По умолчанию корень — сам репозиторий; каталог `src/` без `__init__.py` автоматически добавляется как корень (src-раскладка). Корни можно задать явно: `pmap scan <repo> --root lib --root src`. Использованные корни записываются в карту (`import_roots`).

---

### 2.3. Другие языки (TypeScript / JavaScript, Go, Java, Kotlin, C#, Swift, Dart, Rust, C / C++)

Код не на Python разбирается грамматиками tree-sitter (поле `source` ребра: `tree-sitter-<язык>`). Правила уверенности те же:
- `resolved` — импорт, указывающий на файл проекта; вызов импортированной функции или функции своего пакета; `new X()` класса проекта; вызов метода у `this` или у переменной / поля, чей объявленный тип (или объявленный результат функции проекта) — класс проекта, если ни один подкласс не переопределяет этот метод. Объявленный тип проверяет компилятор, поэтому такой вызов попадает ровно в этот метод.
- `inferred` — тот же вызов, когда метод переопределён в подклассе или тип — интерфейс, протокол или трейт; `candidates` перечисляет варианты. (В Python аннотации компилятор не проверяет, поэтому там вызов через аннотированный тип остаётся `inferred`.)
- `unresolved` — цель неизвестна.

Вызовы в библиотеки и стандартную библиотеку рёбер не дают: зависимость фиксирует импорт (узел `ext:<пакет>`). Идентификаторы содержат путь к файлу: `mod:src/billing/invoice.ts`, `sym:src/billing/invoice.ts:InvoiceService.issue`. Импорт целого пакета (Go, `import a.b.*`, `using A.B;`) связывает файл с теми файлами пакета, которые он действительно использует.

Раздел `languages` фактической карты перечисляет языки проекта: `{"typescript": {"files": 120, "mapped": true}}`. `mapped: false` значит, что грамматика не установлена и файлы этого языка не на карте. Файл, разобранный с синтаксическими ошибками, остаётся на карте и попадает в `errors` с видом `partial_parse`.

## 3. Привязка к коду и контроль устаревания (Staleness)

Каждый узел фактической карты (`external: false`) содержит объект `location`:
```json
{
  "path": "app/services/order_service.py",
  "line_start": 12,
  "line_end": 45,
  "file_hash": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
}
```
- `path`: относительный путь от корня репозитория в POSIX-формате (`/`).
- `line_start`, `line_end`: 1-индексированные номера строк начала и конца определения узла (включая декораторы, если применимо).
- `file_hash`: хэш содержимого **всего файла** на момент сканирования в формате `sha256:<64-hex>`.

**Правило устаревания (Stale Check):**
Если текущий SHA-256 файла на диске отличается от `location.file_hash` узла (или файл удалён), все узлы, привязанные к этому файлу, считаются **устаревшими (`stale`)**. Агент не должен полагаться на `line_start`/`line_end` таких узлов без пересканирования (`pmap scan`).

Карта также считается устаревшей, если в репозитории появился Python-файл, которого в ней нет (или изменился файл из `errors`). Команды `check`, `mermaid` и `context` никогда не используют устаревшую карту молча: они пересканируют репозиторий в памяти и выводят предупреждение.

## 4. Правила соответствия Design → Actual (Mapping Rules)

Проектная карта (`design.yaml`) описывает верхние уровни и правила отображения файлов на подсистемы:

```yaml
pmf_version: "0.1.0"
kind: "design"
project:
  name: "toy_shop"
  description: "Демонстрационный сервис заказов"

subsystems:
  - id: "ui"
    name: "UI / Presentation Layer"
    description: "CLI и HTTP-обработчики запросов пользователя"
    paths:
      - "app/ui/**"
  - id: "services"
    name: "Application Services"
    description: "Бизнес-логика и оркестрация"
    paths:
      - "app/services/**"
  - id: "db"
    name: "Database / Persistence"
    description: "Хранение данных и работа с БД"
    paths:
      - "app/db/**"
  - id: "models"
    name: "Domain Models"
    description: "Общие структуры данных и сущности"
    paths:
      - "app/models/**"

allowed_dependencies:
  - from: "ui"
    to: "services"
  - from: "ui"
    to: "models"
  - from: "services"
    to: "db"
  - from: "services"
    to: "models"
  - from: "db"
    to: "models"
```

### Алгоритм сопоставления и Reflexion Model
1. Каждый внутренний узел `actual`-карты (`external: false`) сопоставляется с `subsystem` по `location.path` с помощью glob-шаблонов в `paths` (`**` означает любую глубину каталогов).
2. Если файл не попал ни в один `subsystem`, он помечается как `unmapped`.
3. Каждое достоверное ребро зависимости (`kind` в `["imports", "calls", "inherits"]`, `confidence == "resolved"`, не `type_only` — если не указан флаг `--include-type-only`) между узлом $u \in S_A$ и узлом $v \in S_B$ ($S_A \neq S_B$) поднимается (lifting) на уровень подсистем как фактическая связь $S_A \to S_B$.
4. **Классификация связей (Murphy & Notkin 1995):**
   - **Convergence (Совпадение):** связь $S_A \to S_B$ есть и в `allowed_dependencies`, и в коде.
   - **Divergence (Расхождение / Архитектурное нарушение):** связь $S_A \to S_B$ обнаружена в коде, но **отсутствует** в `allowed_dependencies`.
   - **Absence (Отсутствующая связь):** связь $S_A \to S_B$ заявлена в `allowed_dependencies`, но в коде нет ни одного подтверждённого ребра между $S_A$ и $S_B$.
5. **Предупреждения.** Отчёт перечисляет всё, что не попало в проверку: неразобранные файлы, неразрешённые импорты, `inferred`/`unresolved` рёбра, пропущенные `type_only` импорты. Отчёт «нарушений нет» при пустом или неполном графе не должен выглядеть как «всё чисто».

## 5. Версионирование и метаданные

В корне `actual.json` обязательно присутствуют поля:
- `pmf_version`: версия спецификации формата в семантическом виде (`"0.2.0"`; 0.2.0 добавила `candidates`, `type_only`, `import_roots`, `errors`). Документы 0.1.x остаются валидными.
- `kind`: `"actual"`.
- `generated_at`: UTC-время генерации в формате ISO 8601 (`"2026-10-17T22:35:00Z"`).
- `scanner`: объект `{ "name": "pmap", "version": "0.3.0" }` — имя и версия инструмента (до 0.3.0 имя было `pmap-python-ast`).
- `languages` (необязательно, с инструмента 0.3.0): языки проекта, `{"<язык>": {"files": N, "mapped": true|false}}`. Поле и вид ошибки `partial_parse` добавлены без смены версии формата: документы 0.2.0 без них остаются валидными.
- `repo_root`: относительный или канонический идентификатор корня, для которого вычислены пути.
- `import_roots`: корни импорта (POSIX-пути относительно репозитория, `.` — сам репозиторий), по которым вычислены имена модулей.
- `errors`: файлы, которые сканер не смог разобрать (`syntax_error`, `decode_error`, `duplicate_module`), с путём, сообщением, строкой и хэшем. Этих файлов **нет** в `nodes`/`edges`; все производные отчёты обязаны сообщать об их наличии.

## 6. Производные представления

### А. Генерация Mermaid-схемы заданного уровня
1. **Уровень `subsystem` (`--level subsystem`):**
   - Узлы графа — подсистемы из `design.yaml` (плюс блок `unmapped`, если есть несопоставленные файлы с зависимостями).
   - Рёбра:
     - **Convergence (Совпадение):** сплошная зелёная/стандартная стрелка `ui -->|imports, calls (3)| services`.
     - **Divergence (Расхождение):** утолщённая красная стрелка `ui ==>|DIVERGENCE: imports (1)| db` с явной визуальной подсветкой (`linkStyle ... stroke:#dc2626,stroke-width:3px`).
     - **Absence (Отсутствие):** пунктирная серая стрелка `ui -.->|ABSENCE| models`.
2. **Уровень `module` (`--level module`):**
   - Подсистемы рендерятся как `subgraph <subsystem_id> ["<Subsystem Name>"]`.
   - Внутри `subgraph` размещаются узлы `module`.
   - Между модулями рисуются `resolved`-рёбра (`imports`, `calls`, `inherits`). Если ребро между модулями нарушает `allowed_dependencies` их подсистем, оно также подсвечивается красным стилем `DIVERGENCE`.

### Б. Компактный текстовый контекст для ИИ-агента (с бюджетом размера)
Чтобы передать структуру проекта в промпт агента с жёстким лимитом `max_chars`, используется **прогрессивное раскрытие**. Элементы добавляются уровнями, пока не исчерпан бюджет:
1. **Сводка.** Название, статус Reflexion-проверки. Все `divergences` выводятся первыми, с файлом и строкой. Неразобранные файлы помечаются `[NOT MAPPED]`.
2. **Пакеты** (каталоги). Первая строка docstring из `__init__.py`, число модулей и пакеты, от которых данный зависит (`uses:`; только `resolved`-рёбра).
3. **Модули.** Одна строка: имя файла, первая строка docstring, до четырёх публичных имён верхнего уровня, длина в строках.
4. **Публичные классы и функции** с сигнатурами и диапазонами строк.
5. **Публичные методы и `__init__`.**
6. **Приватные и dunder-члены.**

Внутри уровня порядок задаёт важность модуля: сначала число **других пакетов**, которые от него зависят, затем число зависящих модулей. Связи внутри пакета о важности почти ничего не говорят, а без этой поправки сгенерированный или шаблонный код вытесняет ядро. Вывод печатается деревом в алфавитном порядке. Последняя строка сообщает, сколько пакетов, модулей и символов не поместилось, и подсказывает `pmap show` / `pmap find`.

Пример (фрагмент для проекта из ~460 модулей при `max_chars=24000`):
```text
# Method Project Map: tallyhub-large (PMF v0.2.0)
Edges listed are statically proven (resolved); inferred/unresolved ones are omitted.
## tallyhub/inventory/ (3 modules) | uses: core, orders
- allocator.py - Chooses the warehouse that ships each item of an order. [AllocationStrategy, PriorityStrategy, NearestStrategy, Allocator] (73 lines)
- stock.py - Stock levels and reservations per (sku, warehouse). [StockLevel, Reservation, StockBook] (70 lines)
## tallyhub/tax/ (3 modules) | uses: core, customers, orders, pricing
- calculator.py - Sales tax on priced orders. [LineTax, TaxResult, TaxCalculator] (77 lines)
... (omitted at max_chars=24000: 0 packages, 228 modules, 3517 symbols; use `pmap show <file path>` or `pmap find <name>`)
```

## 7. Открытые вопросы и зафиксированные решения (v0)

Ниже перечислены пограничные случаи, где в рамках v0 выбран прагматичный вариант, требующий обсуждения перед PMF v1:

1. **Пересечение glob-шаблонов подсистем (`paths`):**
   - *Вопрос:* Что делать, если файл подходит под glob-шаблоны сразу двух подсистем (например, `app/**` и `app/db/**`)?
   - *Решение в v0:* Побеждает наиболее специфичный шаблон (с наибольшим числом сегментов пути до wildcard), а при равенстве — первый по порядку в `design.yaml`. В будущем стоит запретить пересечения на этапе валидации `design.yaml` или ввести поле `exclude`.
2. **Семантика `Absence` для транзитивных или опциональных связей:**
   - *Вопрос:* Является ли `allowed_dependency` обязательным требованием («связь обязана быть в коде») или разрешением («связь допустима, но необязательна»)?
   - *Решение в v0:* По классической модели Murphy & Notkin (1995) отсутствие проектной связи в коде репортится как `Absence`. Однако на практике в `design.yaml` может потребоваться разделение на `required_dependencies` и `allowed_dependencies`.
3. **Гранулярность `file_hash` vs `node_hash`:**
   - *Вопрос:* Сейчас `file_hash` считает SHA-256 всего файла. Если в начале файла добавлена пустая строка или комментарий, все узлы файла становятся `stale`, хотя AST-тело функций не изменилось.
   - *Решение в v0:* Хэшируем весь файл (так как номера строк `line_start`/`line_end` сдвигаются при правке начала файла, а для агента важна точность строк). В v1 можно добавить `ast_hash` тела узла.
4. **Вызовы через `self.<attr>.method()`** — *решено в v0.1:* см. раздел 2.1. Учитываются все присваивания атрибута во всех методах иерархии класса (включая подклассы); `resolved` только если все они — конструкторы одного класса. Присваивание атрибута снаружи класса (`obj.attr = X()`) не отслеживается — это известное ограничение модели «закрытого мира».
5. **Реэкспорты через `__init__.py`** — *решено в v0.1:* ребро `imports` ведёт на модуль, из которого импортируют (`pkg`), а вызов имени прослеживается через цепочку реэкспортов до определяющего символа (`pkg/core.py`).
6. **Хранение проектной и фактической карт в одном файле или раздельно:**
   - *Вопрос:* В концепции упомянуто «две карты в одном формате». При этом проектный файл человек редактирует в YAML (`design.yaml`), а сканер пишет JSON (`.pmap/actual.json`).
   - *Решение в v0:* Обе карты подчиняются единой метамодели и схеме `pmf-v0.schema.json` (различаются полем `kind: "design" | "actual" | "combined"`), что позволяет как хранить их раздельно на диске (`design.yaml` + `.pmap/actual.json`), так и объединять в единый JSON-документ при обмене данными.
7. **Внешний мир не виден сканеру.** Подклассы и вызовы из кода вне репозитория (плагины, пользователи библиотеки), присваивания атрибутов извне, monkey-patching, `__getattr__` модулей. Правила 2.1 консервативны внутри репозитория, но не могут учесть то, чего в нём нет.
8. **Внешние модули определяются по окружению, в котором запущен `pmap`** (плюс `.venv`/`venv`/`env` внутри репозитория). Пакет, не установленный в этом окружении, даёт `unresolved:import:*`. Вопрос: читать ли зависимости из `pyproject.toml`/`requirements.txt`.
